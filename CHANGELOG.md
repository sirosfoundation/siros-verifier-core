# Release record

This file records published testing and production releases. The release
process itself is documented in [`docs/RELEASING.md`](docs/RELEASING.md).

Every published release must receive an entry immediately after its artifacts
are published and verified. Entries include source and artifact identities,
validation evidence, deployment/rollback instructions, known limitations, and
the corresponding documentation updates. Do not add speculative entries for
unreleased work.

### 0.1.0 — 2026-11-11 (cut aborted; superseded by v0.1.1 the same day)

- **Source:** tag [`v0.1.0`](https://github.com/sirosfoundation/siros-verifier-core/releases/tag/v0.1.0) → commit [`c4b49ad`](https://github.com/sirosfoundation/siros-verifier-core/commit/c4b49ad19627fbb1d3830e075fd6cf5c0622de64) (merge of #34; the OpenID4VP 1.0 request fixes `b2b0b18`/`dcbf042`/`f5ff841` behind it). **Signed tag, signature verified** (GPG, `verified: true` on GitHub) — the project's first signed tag.
- **What happened:** the release workflow's validate job passed and the native artifacts attached (the `0.1.0` AAR/POM, the XCFramework + checksum, the Swift bindings). The image build was then **cancelled ~13 minutes in, under a mistaken "wedged build" diagnosis** — the multi-arch image build legitimately runs ~3.5 hours (the `v0.1.0-pre.1` build took 3h36m; `v0.1.1`'s completed normally at the same pace). No image, SBOMs, digest, or certification set were published; **GDC never pinned this release** — its `siros-verifier` fly app has been running a locally built snapshot image (`local-1793576205`, from `d720bb1`), not a GHCR-released digest, throughout.
- **Conformance:** the tag-push conformance run **passed the plan (14/14)**, but its certification hand-off lost the release-creation race — the same structural failure `v0.1.0-pre.1` needed the `workflow_dispatch` re-trigger for. The race is fixed as of #35 (the hand-off now waits for the release); this cut predates that fix's merge.
- **Disposition:** the tag, its signature, and the attached native artifacts stand as the record of the attempt; `v0.1.1` re-cuts the release with identical verifier source plus #35/#36. The process lesson recorded: **establish the baseline before diagnosing a stall.**

Pull-by-digest verified.
- **Native artifacts:** Android AAR/POM `0.1.0-pre.1` in GitHub Packages and on the release; `SirosVerifierCore.xcframework.zip` with its SPM checksum and the generated Swift bindings on the release.
- **Summary:** the first pinnable pre-release — the Phase 0 verifier (HA lifecycle, strict TSL, native ZKP on the blocking pool, the thin JS surface, the recorded soak evidence) in the org-standard Alpine container with the non-root hardening, at a semver pre-release of `v0.1.0`.
- **Validation:**

(The parser-fuzz smoke and the OIDF conformance suite are CI jobs, not validate-job steps; both were green on the release head's CI before the tag — conformance additionally ran on the tag itself, below.)
  - **The OIDF verifier plan passed on the tag: 14/14 modules, 0 failed, 0 skipped** (variant `sd_jwt_vc / x509_hash / direct_post.jwt / request_uri_signed / plain_vp`) — the certification ZIP and run summary are on the release. The first hand-off attempt raced the release creation ("release not found": the conformance workflow finished before the release existed) and was completed by the designed `workflow_dispatch` tag re-trigger — the recovery path the workflow documents; the verdict is the re-run's, on the same tag source.

- **Deployment:** the image was published for digest-pinning, but no GDC deployment ever consumed it — a correction to this entry's original wording (2026-11-11, verified against the sirosid-dev deployment history): the sirosid-dev GDC environment's `siros-verifier` fly app (added to the environment 2026-10-30) has run locally built snapshot images throughout (`local-1793576205`, from `d720bb1`, since 2026-11-01); no GHCR-released digest was ever pinned to it, and `v0.1.1`'s entry below carries the first released-image pin. The loopback-HTTP Compose profile remains the development profile (`docs/INTEGRATORS.md`, now including the file-backed secret permissions the non-root user requires).
- **Rollback:** the first digest-pinnable release; there is no previous published image to roll back to. Remove the GDC deployment, or re-pin when `v0.1.0` publishes.
- **Documentation:** this entry; the Alpine/non-root and secret-permissions guidance in #32; the Sonar cleanups in #31; the soak evidence in `docs/design/SOAK.md`.
- **Known limitations:** the SBOMs on the release (source + container CycloneDX) are **unsigned**: the org-level SBOM workflow's cosign invocation broke on the cosign v2→v3 CLI change — the original run failed at the signing step with `create bundle file: open : no such file or directory`, because the legacy `--output-signature`/`--output-certificate` pair leaves v3's always-written bundle path empty (the v2 `--output-bundle` flag no longer exists in v3; verified against the cosign v3.0.6 source). A later re-run attempt of the release workflow failed earlier still — at SBOM generation, an artifact-download 404 — and never reached signing, so it is not evidence about the signing bug either way; the determinism is the CLI's own flag semantics, and the fix is [sirosfoundation/.github#39](https://github.com/sirosfoundation/.github/pull/39) (the v3 `--bundle` output), with [#40](https://github.com/sirosfoundation/.github/pull/40) adding the container-SBOM signature. This repository now pins the fixed workflow, so `v0.1.0` is set up to ship signed source and image SBOMs — a release requirement to be verified when that tag is cut, with the actual signatures recorded in its own entry. The vulnerability scan results are on the Security tab either way. The `v0.1.0-pre.1` tag itself is an **unsigned** annotated tag (no GPG signature), an exception to `docs/RELEASING.md`'s signed-tag rule — the source link is the commit identity, not tag-signature evidence; the `v0.1.0` tag is required to be signed and its signature verified at release. The pre-release image also predates the `oid4vp` encrypted-response request changes: its request carries no `authorization_encrypted_response_*` parameters anywhere, and that is the shape on the `v0.1.0` release-prep head (#34) — the final [OpenID4VP 1.0 specification](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html) takes the response JWE alg from the chosen `jwks` key's `alg` member (ECDH-ES here) and the enc from `encrypted_response_enc_values_supported`; the JARM names appear nowhere in its text (the 2024 draft clarified by [openid/OpenID4VP#233](https://github.com/openid/OpenID4VP/pull/233) still permitted them as `client_metadata` members — the placement the deployed wallet implements — and the final spec removed them). The interim placement that carried those JARM names inside `client_metadata` (513d459) matched the deployed wallet's draft-era encryption gate but failed the OIDF suite's client-metadata check (9 of 14 modules on its head, all on that one check) and is not in this release. A wallet gating encryption on the legacy `client_metadata` names answers `direct_post.jwt` with a plain `vp_token`, which the verifier refuses — the deployed wallet-frontend must take the final-spec derivation (alg from the `jwks` key, enc from the advertised values) before this release is pinned where that wallet drives.
